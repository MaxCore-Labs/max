## Số đo

### 1. Đối chiếu hiệu năng trước và sau khi tối ưu Schema mục 9

Ở lượt đo đầu tiên giữ nguyên từng chữ `schema.sql` của Spec mục 9, `S4` đã phát hiện 3 điểm nghẽn vật lý khiến `Q = 1.000.000` bị vọt lên `p95 = 57.73 ms` (không đạt `< 20 ms`) và rút `100k` wakeups mất `239.21s`:
1. Thiếu chỉ mục trên `wakeups(run_id)` cho trạng thái `'claimed'` -> mỗi lần `finishRun` phải quét toàn bảng (`FULL TABLE SCAN` 1 triệu dòng) dưới khóa ghi duy nhất.
2. Bảng `wakeups` dùng rowid ngầm định (`id TEXT PRIMARY KEY` không có `WITHOUT ROWID`) + `wakeups_mailbox` thiếu các cột `conversation_id, not_before, attempts, id` -> 20 wakeups của cùng 1 agent nằm rải rác trên 20 trang 4KB khác nhau trong file DB ~250 MB, gây hàng trăm lần đọc/ghi ngẫu nhiên mỗi giao dịch.
3. Chỉ mục `wakeups_due (not_before) WHERE status = 'queued'` đánh chỉ mục cả `1.000.000` wakeup tức thời có `not_before = 0` vào cùng một khóa trùng lặp `0`, làm phình số trang B-Tree bẩn mỗi khi đổi `status = 'claimed'`.

Bảng đo đối chứng trên cùng phần cứng (`100` giao dịch `BEGIN IMMEDIATE...COMMIT` liên tiếp, mỗi giao dịch nhận việc cho `8` agents song song):

| Quy mô hàng đợi `Q` | Schema gốc Spec mục 9 (`p50` / `p95`) | Schema đã tối ưu `S4` (`p50` / `p95`) | Cải thiện `p95` |
|---|---|---|---|
| `Q = 1.000` *(~8 wakeups/tx)* | `2.70 ms` / `4.75 ms` | **`3.02 ms` / `5.28 ms`** *(lần 2: `3.01 / 4.38 ms`)* | Đạt chuẩn |
| `Q = 100.000` *(~160 wakeups/tx)* | `9.35 ms` / `29.52 ms` ❌ | **`4.00 ms` / `5.09 ms`** *(lần 2: `4.51 / 7.07 ms`)* | **Nhanh hơn ~4.2x – 5.8x** |
| `Q = 1.000.000` *(~160 wakeups/tx)* | `23.83 ms` / `57.73 ms` ❌ | **`6.40 ms` / `8.36 ms`** *(lần 2: `6.02 / 8.96 ms`)* | **Nhanh hơn ~6.5x – 6.9x** |
| **Tổng thời gian rút 100k wakeups** | `239.21 giây` | **`39.53 giây`** *(trong đó ~34.4s là ngủ giả lập)* | **Nhanh hơn 6.0x** |

### 2. Kết quả `EXPLAIN QUERY PLAN` thực tế

```text
[1a. Candidate Agents (natural JOIN)]
  |-- (7<-0) SCAN a USING INDEX agents_ready
  |-- (16<-0) BLOOM FILTER ON t (id=?)
  |-- (25<-0) SEARCH t USING INDEX sqlite_autoindex_teams_1 (id=?)

[2. Agent Mailbox Top Wakeup]
  |-- (4<-0) SEARCH wakeups USING COVERING INDEX wakeups_mailbox (agent_id=?)

[3. Recompute Agent Ready]
  |-- (4<-0) SEARCH wakeups USING COVERING INDEX wakeups_mailbox (agent_id=?)

[4. FinishRun Complete Claimed Wakeups]
  |-- (5<-0) SEARCH wakeups USING INDEX wakeups_run (run_id=?)

[5. Boot Recovery Running Runs]
  |-- (3<-0) SEARCH runs USING INDEX runs_active (status=?)
```

## Quyết định

- **Xác nhận kiến trúc Actor trên SQLite của Spec `8.2` hoàn toàn khả thi và vững chắc** cho quy mô `5.000` agents và `1.000.000` wakeups trên đúng 1 kết nối ghi (`SetMaxOpenConns(1)` + `_txlock=immediate`) kết hợp pool kết nối đọc riêng (`SetMaxOpenConns(8)`).
- **Cấu hình PRAGMA chuẩn chốt cho `P1.04` (`internal/adapter/sqlite`)**:
  - Kết nối ghi (1 conn): `_pragma=journal_mode(WAL)&_pragma=synchronous(NORMAL)&_pragma=foreign_keys(1)&_pragma=busy_timeout(5000)&_pragma=cache_size(-65536)&_pragma=mmap_size(268435456)&_pragma=wal_autocheckpoint(4000)&_txlock=immediate` *(lưu ý: không qua `url.Values.Encode()` để tránh mã hóa dấu ngoặc `(` thành `%28`)*.
  - Chạy `ANALYZE` (hoặc `PRAGMA optimize`) sau khi khởi tạo/di trú để bộ lập kế hoạch của SQLite luôn duyệt `agents_ready` làm vòng ngoài thay vì quét bảng `teams` trước.

## Việc phải sửa trong spec/kế hoạch

1. **Cụm hóa vật lý bảng `wakeups` theo `agent_id` (`Spec mục 9` / `P1.04`)**: Đổi khóa chính của bảng `wakeups` từ `id TEXT PRIMARY KEY` sang **`PRIMARY KEY (agent_id, id) WITHOUT ROWID`**. Toàn bộ các wakeup thuộc cùng một agent sẽ nằm liền kề nhau trên cùng 1–2 trang lá B-Tree bất kể `Q` lớn tới hàng triệu dòng, triệt tiêu hoàn toàn ghi ngẫu nhiên rải rác khi `claim` và `finish`.
2. **Nâng `wakeups_mailbox` thành Covering Partial Index & bổ sung `wakeups_run` (`Spec mục 9` / `P1.04`)**:
   - Đổi `wakeups_mailbox` thành:
     `CREATE INDEX wakeups_mailbox ON wakeups (agent_id, priority DESC, created_at, conversation_id, not_before, attempts, id) WHERE status = 'queued';`
   - Thêm chỉ mục riêng phần cho các wakeup đang chạy để `finishRun` và bước khôi phục không quét bảng:
     `CREATE INDEX wakeups_run ON wakeups (run_id, agent_id) WHERE status = 'claimed';`
3. **Thu hẹp điều kiện chỉ mục `wakeups_due` (`Spec mục 9` / `P1.04`)**: Đổi `WHERE status = 'queued'` thành **`WHERE status = 'queued' AND not_before > 0`**. Các wakeup tức thời (`not_before = 0`) đã cập nhật thẳng `agents.ready = 1` ngay trong `Wake()` nên không bao giờ cần scheduler quét; loại bỏ chúng khỏi `wakeups_due` giúp giảm một nửa chi phí cập nhật chỉ mục trên đường găng.
4. **Tính lại `agents.ready` ngay trong giao dịch nhận việc (`Spec 8.2.2` / `P1.09`)**: Để giữ bất biến *"không có wakeup `queued` đến hạn nào thuộc agent có `ready = 0`"* và ngược lại không để `ready = 1` ảo khi hộp thư đã rút hết, hàm `recomputeAgentReadyTx` cần gọi ở cả 4 điểm: cuối `Wake()`, cuối `Claim()`, cuối `FinalizeRun()`, và cuối `RecoverOnBoot()`.
5. **Tách biệt `attempts` khi server khởi động lại với lỗi của run (`Spec 8.2.5` vs `8.3` / `P1.09`)**: Khi chính tiến trình `max` tắt/khởi động lại (deploy bản mới hoặc mất điện — `8.2.5`), các wakeup `claimed` đang bay dở bị trả về `queued` không phải do lỗi của task/agent; không nên cộng dồn vào trần `attempts >= 3` (`dropped`) để tránh việc restart dịch vụ 3 lần làm đánh rơi oan các task lành mạnh.
